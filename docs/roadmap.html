Motor Control Lab · product roadmap · November 2026

From lessons to mastery to real builds

The app already teaches well: every lesson pairs theory with a live simulation, a quiz, numeric challenges, a debugging case and a proof-of-work task. What it lacks is what happens after a lesson: remembering it, knowing when you have mastered it, writing real control code, and carrying a hardware build through to a finished result you can show.

Where the learning loop breaks

The lesson page covers understanding well. The dashed steps below are where a learner currently drops out of the app and has to manage alone.

Read theory→ Play the sim→ Worked example→ Quiz→ Challenge→ Debug case→ Write the code→ Review in 3 days→ Mastery check→ Build project→ Track the build→ Portfolio
Exists todayProposed

What the code tells us

  • Progress is one flat XP number in localStorage (emk-progress-v2). It counts completion, not retention.
  • Quiz items and challenges are answered once and never come back, so most of what is learned in week 2 is gone by week 9.
  • The Live lab FOC model in lib/sim/lab.ts is the app's best asset, but only the app's own code drives it. Learners can never put their own controller in the loop.
  • Projects are good static briefs with no way to record progress, measurements or spend.
  • Lessons have no prerequisite links, so the 13-week route is the only map.

Home becomes “Today”

The landing page stays for first visits. Once progress exists, home opens on what to do next.

  1. Review queue first: the one habit that keeps earlier tracks from fading. Card count and time estimate come from the scheduler.

  3. Mastery replaces the single XP bar as the main progress signal. XP stays in the header.

Lesson additions

The existing layout stays. Two blocks and one overlay are added.

/sandbox/[exercise]

Firmware sandbox

The step from understanding FOC to writing it. The learner's function replaces the controller inside the existing Live lab motor model.

  1. Eight exercises in the order a real drive is brought up, each unlocked by the one before.
  2. Editor with typed helpers (clarke, park, svpwm) available from exercise 3 on. The same code style ports almost directly to C on an STM32.
  3. Reference (dashed) against the response, using the Live lab plot style.
  4. Pass or fail tests with measured values, so the feedback is a number rather than a judgement.

/projects/[id]/work

Project workspace

Starting a project turns its brief into a tracker. Everything stays in the browser and can be exported as one JSON file.

  1. Milestones with acceptance criteria written as checks you can measure. A milestone closes only when every check is ticked.
  2. Lab notebook entries with time, text, photos and CSV logs that draw a quick plot.
  3. Parts list with planned and actual cost in ₹, plus the rubric self-review from section 04.

/arena

Fault-hunt arena

Turns the existing Live lab missions into practice that can be replayed. Each round picks a random motor and a random fault, so memorising answers does not help.

  1. Telemetry from lib/sim/lab.ts with randomised motor parameters from a seed.
  2. Each instrument costs points, which rewards choosing the most informative test first, as on a real bench.
  3. Advanced rounds combine two faults. Scores and best times go to the portfolio.
04

Ten new projects, from beginner to advanced

Chosen to fill the coverage gaps in section 01: the two lessons with no project (AC phasors, induction motors) and the five with only one. Each one uses the app's Project fields, plus three new fields: milestones with acceptance checks, pitfalls, and prereqs. Budgets are rough Indian-market figures in ₹, like the existing ones; ₹0 means software only.

#ProjectLevelWeeksBudgetLessons it applies

One rubric for every project deliverable

Scored 1–4 in the workspace for self-review. A score of 3 on all four criteria marks the project Applied on the lessons it links to.

CorrectnessDoes it work, and do the acceptance checks pass with real numbers?
MeasurementAre units, uncertainty and test conditions stated? Could someone repeat it?
ExplanationIs the result tied to the lesson's equations, with any mismatch explained?
Safety and methodCurrent limits, fusing, guarding and a clean bring-up order.
05

Data model changes

Everything stays as TypeScript content plus browser storage, as today. Only the tutor needs a server route. Changes to lib/content/types.ts, lib/content/projects.ts and components/ProgressProvider.tsx:

// lib/content/types.ts
interface Lesson {
  …existing fields
  requires?: string[];          // lesson ids → skill map edges (F1)
  worked?: { prompt: string; steps: string[]; answer: string };  // F2
  formulas?: string[];          // ids into lib/content/reference.ts (F3)
  gen?: (seed: number) => ChallengeItem;  // fresh numbers for checkpoints (F9)
}

// lib/content/projects.ts
interface Project {
  …existing fields
  prereqs?: string[];           // lessons to master first
  milestones?: { title: string; accept: string[] }[];  // workspace checks (F12)
  pitfalls?: string[];
}

// localStorage "emk-progress-v3", migrated from v2 on first load
interface ProgressV3 {
  xp: number;                                  // kept
  lessons: Record<string, { quiz: number; chal: number; debug: boolean; pow: boolean; worked: number }>;
  cards: Record<string, { box: 1|2|3|4|5; due: string; lapses: number }>;   // F5, Leitner boxes
  workspaces: Record<string, { started: string; checks: Record<string, boolean>;
                               notes: Note[]; spend: Record<string, number>; rubric?: number[] }>;
  sandbox: Record<string, { code: string; passed: boolean }>;
  arena: { best: number; rounds: number };
}

// Mastery is derived, never stored:
// Seen       → opened the lesson
// Practised  → quiz ≥ 80 % and every challenge solved
// Applied    → also a sandbox exercise or a linked project at rubric ≥ 3
// Mastered   → also its review cards reached box 4 (about 3 weeks of spacing)
Ready to append to PROJECTS in lib/content/projects.ts.
